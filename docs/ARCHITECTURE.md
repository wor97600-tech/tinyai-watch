# 架构说明

## 目标与约束

| 约束 | 影响 |
| :-- | :-- |
| 完全离线 | 不能调任何云端 API，模型必须随包分发 |
| 内存以 MB 计 | 不建倒排索引、不加载多余权重、消息列表限长 |
| 无 GPU | 推理是纯 JS 的 `Float32Array` 矩阵乘 |
| 前台/后台都会被系统回收 | 熄屏要主动停流式、收输入法 |

## 分层

```text
pages/Home/index.ux      UI + 状态 + 生命周期
        │
        ├─ ai/reply_engine.js    决策：这句话怎么答
        ├─ ai/simple_kb.js       检索：知识库打分
        ├─ ai/char_predictor.js  生成：字符接龙
        └─ input/pinyin_engine.js 输入：拼音 → 候选字
```

`index.ux` 只负责「拿到一句话、显示一句话」，所有决策都在 `reply_engine`。
这样回复策略可以脱离手表界面在 Node 里直接测。

## 对话决策顺序

1. **纯模型模式**（用户显式开启）→ 只用字符模型，用来观察模型真实水平
2. **算术 / 时间** → 确定性答案，查表最快
3. **诗句 / 接龙 / 梗** → 创意类输入走素材库
4. **闲聊意图** → 37 条意图正则，命中即回，且避免复读
5. **知识库** → 80 条条目，bigram 命中打分；低分命中会被问句/日常层否决，防止答非所问
6. **日常陈述** → 178 条，处理「今天好累」这类不需要知识的问题
7. **字符接龙** → 前面都没命中时，用模型把话接下去
8. **保底** → 一定返回一句人话，永不出现「我不知道」

## 检索为什么不用 TF-IDF

早期版本建过完整倒排表，250 条条目在手表上直接把内存打满。
现在的做法是：常驻只保存条目文本，查询时现算 bigram 命中，单次查询在毫秒级。

## 模型为什么是定长前向网络

GRU 在手表上实测跑不动：长序列逐步推理会长时间占用主线程，界面掉帧甚至整机卡死。
定长 8 字上下文的前馈网络每次只做一次矩阵乘，耗时稳定可预测。

## int8 量化

训练在电脑端完成（float32），打包时按输出通道做 per-channel 量化，
权重 1.07 MB → 307 KB，Top-1 损失小于 0.5 个百分点。

## 生命周期

`onHide`：记录是否在回复中 → 停看门狗 → 取消流式 → 关键盘 → 收起官方输入法
`onShow`：官方键盘模式重新接上输入框；若刚才被打断，补一句说明
`onDestroy`：清定时器、清看门狗、落盘聊天记录
